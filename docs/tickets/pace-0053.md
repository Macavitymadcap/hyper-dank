## Summary

Add the accepted second wave of shared UI primitives from the app-builder readiness audit so
server apps, dashboards, docs sites, static blogs, and demos can assemble common app shells,
navigation, status surfaces, data summaries, and content pages from public Hyper-Dank components.

This ticket builds on `pace-0052`; it should use the new action, form, icon, validation, and
Storybook patterns rather than inventing parallel conventions.

## Goals

- Improve existing shared primitives: `Accordion`, `PopoverMenu`, `ScrollableTable`,
  `CompactList`, and `LabelledOutput`.
- Add accepted layout primitives: `AppShell`, `PageHeader`, `SectionHeader`, and `Toolbar`.
- Add accepted navigation primitives: `Breadcrumbs`, `Tabs`, `SideNav`, and `Pagination`.
- Add accepted overlay and feedback primitives: `Dialog`, `Notice`, `StatusSummary`, `Progress`,
  `LoadingIndicator`, and `EmptyState`.
- Add accepted data and content primitives: `StatBlock`, `MetadataList`, `TimelineList`, `Prose`,
  `CodeBlock`, and `Callout`.
- Keep every component native-first, server-rendered, HTMX-friendly where useful, and graceful
  without JavaScript or HTMX.
- Add public exports, focused render tests, CSS hooks, package README notes, compatibility coverage,
  and Storybook examples for the new public API.

## Non-Goals

- No toast/snackbar region, tooltip, date picker, autocomplete, data grid, tree view, chart, stepper,
  wizard, or rich text editor work.
- No data provider, repository, transport, automation, static-content, or public docs-site
  implementation; those start in later `pace-0054` through `pace-0059` tickets.
- No app-specific route names, domain copy, fixtures, auth assumptions, or persistence behaviour.
- No replacement for app-owned layout CSS. Shared CSS should provide stable hooks and minimum
  ergonomics, not a full product theme.
- No custom modal framework: `Dialog` must use native `<dialog>` under the hood.

## Public API Requirements

- Additive exports from `@macavitymadcap/hyper-dank-ui`.
- No private app names, private route names, or app-specific nouns in component names, props,
  examples, tests, stories, or README copy.
- Components should accept plain JSX content, links, actions, and metadata from consuming apps
  rather than owning data fetching, routing, or persistence.
- CSS class hooks and semantic CSS variables must be documented through tests and Storybook.
- Package README lists the new exports and keeps usage boundaries concise.
- Compatibility coverage imports representative new exports through the public package boundary.
- Storybook is the canonical component reference; public docs should link there rather than
  duplicating component detail.

## Dialog Contract

`Dialog` should use native `<dialog>` under the hood and provide a small, explicit composition
surface:

- trigger button or trigger content that can open the dialog when JavaScript is present;
- native content inside `<dialog>` with labelled title and optional description;
- close action using the native `method="dialog"` pattern where practical;
- optional HTMX attributes on trigger or body actions for progressively enhanced server workflows;
- graceful fallback content or link/action path when JavaScript is unavailable.

Browser/focus tests should cover the trigger, opened state, close behaviour, and keyboard reachability
when the implementation includes client-side glue.

## Rollout Notes

- Prefer composition over configuration when component options become app-specific.
- Use existing `HtmxProps`, `Button`, `LinkButton`, `IconButton`, `Fieldset`, `ValidationSummary`,
  and icon catalogue patterns from `pace-0052`.
- Treat Storybook examples as generic app-builder examples, with domain components kept separate in
  reference-app sections.

  before implementation continues.
