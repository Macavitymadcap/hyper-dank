## Summary

Deepen `@macavitymadcap/hyper-dank-data` so app builders can create database providers,
repository contracts, migration stores, and adapter conformance tests with less repeated
boilerplate. The package should stay domain-neutral: applications still own schemas, queries,
transactions, repository method names, seed data, and storage adapters.

This ticket builds on the existing `DatabaseLifecycle`, `RepositoryFactory`,
`DatabaseProviderBase`, `MigrationStore`, and `describeDatabaseLifecycleContract` exports. It should
lift only the reusable patterns already visible in the Walking Pace provider and repository
contracts, without turning the data package into an ORM.

## Goals

- Add generic repository contract types for common CRUD-like app repositories where they help type
  app-owned repositories without forcing a schema or method naming style.
- Add provider factory and registry helpers that make environment-based provider selection easier
  while keeping apps in charge of adapter construction and required environment variables.
- Expand migration helpers with validation, duplicate id detection, pending-plan reporting, and
  dry-run metadata that can be used by SQLite, Postgres, or future adapters.
- Move reusable repository/provider conformance harness shapes into
  `@macavitymadcap/hyper-dank-data/testing` so apps can write contract tests like the current
  Walking Pace adapter suites without importing app internals.
- Update package exports, README coverage, public docs compatibility examples, and consumer tests
  for the new data package API.

## Non-Goals

- No ORM, query builder, SQL DSL, schema generator, model mapper, or migration file format.
- No Walking Pace domain repository methods, walk stats, invitation schema, auth tables, or seed
  data in the shared data package.
- No app-specific provider selection logic such as `DATABASE_URL` versus `DB_PATH` baked into the
  package; helper APIs may accept app-provided environment resolvers.
- No transaction abstraction unless implementation proves a small adapter-neutral helper is useful
  across SQLite and Postgres without overpromising behaviour.
- No production data migration or table change for the reference app.
- No breaking changes to existing `@macavitymadcap/hyper-dank-data` exports.

## Public API Requirements

- Additive exports from `@macavitymadcap/hyper-dank-data`.
- Additive testing exports from `@macavitymadcap/hyper-dank-data/testing`.
- Public names must be domain-neutral and should not mention Walking Pace, private consuming apps,
  auth products, or a particular storage backend unless the type is explicitly backend-specific.
- Helper APIs must preserve app ownership of schemas, SQL, transactions, environment variables, and
  repository method names.
- Package README and docs must include full descriptions for new functions, types, parameters,
  return values, errors, and examples rather than relying on broad summary tables.
- Consumer compatibility coverage must import representative new exports from the packaged public
  boundary.

## Candidate Interfaces

The exact names may change during implementation if tests reveal a clearer shape, but the ticket
should stay within this boundary:

- `RepositoryContract<TRecord, TId>` or narrower `ReadableRepository` / `WritableRepository`
  interfaces for common app-owned stores.
- `RepositoryHarness<TRepository>` and setup/cleanup types for adapter conformance tests.
- `DatabaseProviderFactory<TProvider, TEnvironment>` and a small provider registry or selector
  helper that calls app-owned factory functions.
- `MigrationRegistry` and `MigrationPlan` helpers that validate ordered migrations, detect
  duplicate ids, and describe pending/applied/skipped migrations.
- Reusable testing helpers for lifecycle checks, repository harness cleanup, and provider factory
  selection behaviour.

Avoid abstract base classes unless the implementation proves they remove meaningful repeated
lifecycle code without hiding adapter details.

## Implementation Notes

- Start in `libs/database/src/index.ts`, `libs/database/src/testing.ts`, and
  `libs/database/README.md`.
- Prefer small pure helpers and interfaces over inheritance.
- Use fake in-memory providers and repositories for package-level tests so the shared package stays
  backend-neutral.
- Only update `apps/walking-pace/src/db` if doing so demonstrates the shared helpers without making
  the reference app harder to read.
- Keep docs language explicit that the package helps with lifecycle, migration, and test mechanics;
  it does not own application data modelling.

## Acceptance Criteria

- `@macavitymadcap/hyper-dank-data` exports additive repository, provider, and migration helper APIs.
- `@macavitymadcap/hyper-dank-data/testing` exports reusable harness helpers for app-owned provider
  and repository conformance tests.
- Existing `DatabaseLifecycle`, `RepositoryFactory`, `DatabaseProviderBase`, `Migration`,
  `MigrationStore`, `runPendingMigrations`, and `describeDatabaseLifecycleContract` remain
  backwards compatible.
- Migration helpers can validate duplicate ids and produce pending/applied plans without executing
  migrations.
- Package README and public docs describe the new APIs, usage boundaries, errors, and examples.
- Consumer compatibility tests import representative new exports through the packaged public data
  package boundary.
- Walking Pace database provider and repository tests still pass.
- `bun run verify` passes before the implementation PR is marked ready.
