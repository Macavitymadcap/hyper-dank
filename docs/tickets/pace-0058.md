## Summary

Tidy the public docs estate so app builders can understand Hyper-Dank without tripping over stale
internal process notes, private-consumer references, shallow package descriptions, or mixed audience
signals. The docs site should explain the framework philosophy, package boundaries, non-UI API
contracts, Storybook handoff, deployment posture, and generated/static-content guidance. Package
READMEs and repo-level docs should stay concise, current, and aimed at their own readers.

## Goals

- Remove private consuming-app references from public docs, package READMEs, Storybook guides if
  touched, and repo-level public docs; use generic shapes such as server app, static blog,
  dashboard/admin, static demo, reference app, script consumer, and static-content generator.
- Expand non-UI library pages for data, transport, automation, and automation/content with
  JSDoc-style prose descriptions for functions, classes, types, methods, parameters, return values,
  errors, examples, and boundaries.
- Keep component details in Storybook and use docs-site UI pages as overview and navigation into the
  canonical component reference.
- Turn `site/system.md` into a stronger framework philosophy page covering HTML-first flow, Hono,
  HTMX, Bun, Storybook, package boundaries, native fallbacks, testing, and app-owned responsibilities.
- Rework `site/verification.md` so it serves public adopters with recipe-level verification guidance
  rather than internal gate minutiae.
- Audit and update `README.md`, `ARCHITECTURE.md`, `CONTRIBUTING.md`, and package READMEs for
  audience fit, current package names, branch flow, verification expectations, release/deployment
  posture, and links to richer docs.
- Keep public copy plain, current, and British English where prose choices matter.

## Non-Goals

- No new shared package APIs.
- No Storybook component-reference expansion beyond links or wording needed to keep docs consistent;
  that belongs to `pace-0057`.
- No new app-builder recipe set or compatibility examples; that belongs to `pace-0059`.
- No visual redesign of the docs site beyond layout or navigation tweaks required for clearer API
  reference pages.
- No removal of maintainer-only process detail from internal docs where it still helps contributors.
- No private consuming app names, private domains, or private roadmaps in public-facing docs.

## Public API Documentation Requirements

- Use prose descriptions for classes, interfaces, functions, methods, types, parameters, return
  values, errors, examples, and adoption boundaries.
- Use tables for summaries only; do not make a table the only API reference for non-UI packages.
- Document additive exports and subpaths added earlier in the epic:
  - `@macavitymadcap/hyper-dank-data`
  - `@macavitymadcap/hyper-dank-data/testing`
  - `@macavitymadcap/hyper-dank-transport`
  - `@macavitymadcap/hyper-dank-automation`
  - `@macavitymadcap/hyper-dank-automation/content`
- Keep examples app-neutral. Suitable examples include server app routes, static blog pages,
  dashboard/admin lists, static demos, local scripts, and static-content generation.
- State what remains app-owned: schemas, repositories, auth, permissions, route names, fixtures,
  deployment targets, content taxonomy, release policy, and product copy.
- Link component detail to Storybook rather than duplicating all component prop documentation in the
  docs site.

## Private Reference Rules

Public docs, package READMEs, public Storybook guides, and repo-level public docs must not mention:

- Private consuming app names.
- Private roadmap details or migration plans.
- Private domain terms that make examples look product-specific.
- Compatibility test names that reveal private apps.

They may mention:

- Hyper-Dank.
- The Walking Pace reference app when the document is explicitly describing the local reference app,
  static demo, or Storybook reference-app examples.
- Generic consumer shapes such as server app, static blog, dashboard/admin, static demo, reference
  app, script consumer, and static-content generator.

## Implementation Notes

- Start with a small private-reference and link-health check if the repo has a suitable docs-check
  script to extend; otherwise add a focused Bun script/test with clear allow-lists.
- Read generated output where practical, not only source Markdown, because navigation and relative
  links can fail after rendering.
- Keep package READMEs concise. Move deep API explanations to public docs pages unless the package
  README is the best first-contact surface.
- Keep `README.md`, `ARCHITECTURE.md`, and `CONTRIBUTING.md` distinct: adopter overview,
  maintainer architecture, contributor workflow.
- Update `site/verification.md` by separating public verification strategy from internal local gate
  details. Internal details can remain in `CONTRIBUTING.md`, `README.md`, script docs, or
  architecture notes where they help maintainers.
- If docs changes affect public page layout or navigation, include focused screenshots in the PR
  evidence rather than full-page captures that hide the changed area.

## Acceptance Criteria

- Public docs and package READMEs contain no private consuming-app references or private roadmap
  details.
- `site/system.md` reads as the main Hyper-Dank framework philosophy page.
- `site/verification.md` gives public adopters useful verification guidance without being an
  internal process dump.
- Non-UI library pages include prose API descriptions for relevant classes, interfaces, functions,
  methods, parameters, return values, errors, examples, and app-owned boundaries.
- UI library docs point to Storybook for detailed component reference instead of duplicating it.
- Package READMEs and repo-level docs are current for package names, exports, scripts, branch flow,
  verification, release, deployment, and documentation locations.
- Focused docs checks, static docs build, a11y review, and representative screenshots pass for the
  changed public docs surfaces.
- `bun run verify` passes before the implementation PR is marked ready.
