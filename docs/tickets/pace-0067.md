## Summary

Move Hyper-Dank's project-management source of truth from repository Markdown ticket files towards
GitHub Issues and GitHub Projects. Markdown should remain valuable for durable epic briefs,
architecture notes, and implementation records, but future ticket state, assignment, dependencies,
labels, and review flow should live in GitHub where the work is planned and merged.

## Goals

- Reconcile the existing `pace-*` ticket history so skipped-looking numbers, hotfix epics, parallel
  branches, implemented tickets, and unused/reserved IDs are documented before migration.
- Define the GitHub Issues model for epics, tickets, hotfixes, audits, follow-ups, and release
  chores.
- Decide whether new GitHub-managed work should keep the historical `pace-*` identifiers or move to
  a Hyper-Dank-native prefix such as `hyper-dank-*` or `hd-*`.
- Define a GitHub Projects board or table shape with status, parent epic, priority, type, package
  area, target branch, PR, verification, and release-impact fields.
- Add or update issue templates, PR template guidance, labels, and contributor docs so new work is
  created and tracked in GitHub first.
- Document how Markdown planning docs should be used after migration: durable decisions and
  architecture records, not the operational ticket tracker.

## Non-Goals

- No immediate deletion of historical `docs/tickets` or `docs/epics` files.
- No bulk GitHub issue creation until the desired issue/project model is reviewed.
- No replacement of branch protection, Conventional Commit titles, or PR checks.
- No change to package release automation or `release-please`.
- No requirement that every small hotfix has a full Markdown ticket after the GitHub workflow is in
  place.

## GitHub Tracking Model

The implementation should decide the final names, but the target shape should cover:

| Concept | GitHub Home | Notes |
| --- | --- | --- |
| Epic | Issue plus project item | Owns summary, goals, non-goals, ticket list, target branch, and release impact |
| Ticket | Issue plus project item | Owns acceptance criteria, affected areas, verification, branch, and PR link |
| Hotfix | Issue or PR-linked issue | Can stay lightweight when scope is urgent and narrow |
| Audit | Issue plus optional Markdown artefact | Findings may live in docs when they need long-term reference |
| Architecture decision | Markdown doc linked from issue | Durable decisions stay versioned in the repo |
| Follow-up | Issue | Can be triaged without creating a branch or Markdown file |

## Identifier Prefix Decision

GitHub migration is a good point to stop using a Walking Pace-derived prefix for new project
tracking if that keeps Hyper-Dank clearer. `pace-*` should remain valid for historical branches,
docs, PRs, and release notes, but future GitHub issues may use a new prefix if the migration accepts
one.

Candidate options:

| Prefix | Example | Trade-off |
| --- | --- | --- |
| `pace-*` | `pace-0068` | Preserves continuity, but keeps the old reference-app identity in new Hyper-Dank work |
| `hyper-dank-*` | `hyper-dank-0001` | Clear and explicit, but verbose in branch names and PR titles |
| `hd-*` | `hd-0001` | Short and Hyper-Dank-specific, but less self-explanatory outside the repo |

The accepted convention should state how to name GitHub issues, branches, PR titles, labels,
project fields, and any remaining Markdown artefacts. It should also explain whether numbering
continues from the `pace-*` sequence or starts fresh under the new prefix.

## Acceptance Criteria

- Existing ticket history gaps are reconciled and documented.
- Future work has a GitHub Issues and Projects source-of-truth model.
- Issue templates and project fields are specified, and local template files are added or updated
  where appropriate.
- `CONTRIBUTING.md` explains how to start work from GitHub, branch from the correct base, link PRs
  back to issues/projects, and keep Markdown docs for durable decisions.
- The workflow either preserves `pace-*` for new work or adopts a new `hyper-dank-*` / `hd-*`
  identifier convention with explicit branch, issue, PR, and historical-reference rules.
- Historical Markdown docs remain intact unless a separate migration ticket explicitly archives or
  restructures them.
- Any branch-flow or PR-template changes are verified with the existing workflow expectations.

## Assumptions

- The maintainer wants GitHub to own operational ticket state going forward.
- The first implementation can document and template the workflow before doing a bulk issue/project
  migration.
- GitHub project creation may require manual setup or an authenticated `gh` step outside local test
  coverage.
