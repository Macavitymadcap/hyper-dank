## Summary

Rework Storybook so it feels like the canonical consumer reference for
`@macavitymadcap/hyper-dank-ui`, not a shelf of internal examples. Component docs should state what
the component guarantees, how it behaves in light/dark themes, how it handles accessibility, and how
it composes with HTMX-friendly server-rendered apps.

## Goals

- Apply the `pace-0061` Storybook classification: keep consumer references, move/reframe
  maintainer material, and label Walking Pace examples as reference-app composition.
- Improve shared component docs with props, variants, children/slots, semantic output, class/CSS
  hooks, accessibility notes, HTMX/native fallback behaviour, and examples.
- Rework guide and philosophy pages to use Hyper-Dank components where practical without making the
  docs awkward.
- Improve icon catalogue scanability, naming, copyability, and light/dark review.
- Ensure theme or mode controls affect relevant Storybook pages and that representative interaction
  checks still pass.

## Non-Goals

- No new shared UI primitives unless a tiny additive fix is required to document an existing public
  component accurately.
- No public docs-site navigation work; that belongs to `pace-0065`.
- No package README installation rewrite; that belongs to `pace-0062`.
- No visual rebrand of Storybook beyond consumer-reference clarity and component consistency.

## Acceptance Criteria

- Storybook top-level groups and pages match the accepted `pace-0061` classification.
- Shared component docs include useful contracts for props, output, accessibility, CSS hooks,
  theme behaviour, examples, and HTMX/native fallbacks where relevant.
- The icon catalogue is easier to scan, compare, and use in examples.
- Internal maintainer material is moved out of consumer flow or rewritten for adopter value.
- Walking Pace content is clearly labelled as reference-app composition.
- `bun run test:storybook` passes, and screenshots are refreshed where visible changes warrant it.

## Assumptions

- Storybook remains the canonical rendered reference for UI components.
- Component API changes should be small and additive; larger component work belongs in a follow-up
  ticket or epic.
