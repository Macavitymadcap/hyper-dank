## Summary

Audit the public Hyper-Dank surfaces before rewriting them. The ticket should classify current docs,
Storybook pages, package READMEs, package exports, and package metadata so the rest of the epic is
based on discovered facts rather than assumptions.

## Goals

- Classify every current docs-site page, package README, repo-level doc, and Storybook top-level
  page as adopter reference, maintainer guidance, project history, recipe, API reference, or
  removable/reframeable material.
- Verify the current package consumption truth from `package.json`, package export maps, pack
  scripts, workspace usage, and any visible publication metadata.
- Record whether each package is published to npm or another registry today. If a package is not
  published, classify the viable Campaign Ledger consumption routes and recommend one for
  `pace-0062`.
- Answer the captured `pace-0060` questions about Testing Pipelines, Component Philosophy,
  reference map, App Builder Reuse, icon catalogue, second-wave primitives, Surfaces and Metadata,
  Disclosure and Menu, About, recipes, and library sidebar behaviour.
- Produce an accepted coverage map for docs pages, package READMEs, Storybook sections, package
  API reference, and checks to be implemented in later tickets.

## Non-Goals

- No broad docs rewrite beyond small audit notes and obvious dead-link fixes.
- No package publication, release automation, or external registry work.
- No Storybook redesign or component API changes.
- No new public package exports.

## Audit Questions

- What can a new developer install or consume today without being inside this monorepo?
- Which pages explain adoption, and which pages explain maintainer workflow?
- Which public exports lack docs, examples, or compatibility evidence?
- Which Storybook pages demonstrate reusable components, and which are internal process notes?
- Which docs pages duplicate each other, and which page should own the canonical explanation?
- Which checks can be automated cheaply without adding brittle docs infrastructure?

## Acceptance Criteria

- The audit records every docs-site page, package README, root-level public doc, and Storybook group.
- Current package distribution and consumption status is stated plainly from repo evidence.
- The audit recommends a concrete Campaign Ledger installation route for `pace-0062`.
- All captured questions in `pace-0060` are answered or converted into explicit follow-up work.
- A page/API/check coverage map is accepted for `pace-0062` through `pace-0066`.
- No public docs copy overpromises npm publication, starter templates, or distribution guarantees.

## Assumptions

- The audit can rely on local repo metadata unless external registry verification is explicitly
  needed by the implementation ticket.
- Package publication or template generation work will be separate from this epic unless the audit
  proves current docs cannot be made truthful without it.
