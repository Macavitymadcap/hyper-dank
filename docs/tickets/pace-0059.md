## Summary

Finish the app-builder epic by turning the public recipes page and compatibility tests into a clear,
shared adoption map. The docs should show how to compose Hyper-Dank packages for realistic app
shapes, while consumer-style tests prove those examples import from the public package boundaries
instead of relying on monorepo internals.

## Goals

- Expand `site/recipes.md` into practical app-builder recipes for server apps, static blogs,
  dashboard/admin tools, static demos, script consumers, and static-content generators.
- Tie each recipe to public package imports and explicit app-owned responsibilities.
- Add or reorganise consumer-style compatibility tests so every documented recipe shape is protected
  through package paths.
- Rename or split the current `e2e/consumer-compat/character-sheet-compat.test.tsx` coverage where
  useful so app-neutral recipe compatibility is not hidden behind a private-consumer filename.
- Include examples that cover UI, data, transport, automation, and automation/content boundaries
  without leaking private consuming app names or domain details into public docs.
- Keep recipes concise and useful: show composition, boundaries, verification, and where to go next,
  not a full starter app or copy-paste framework.

## Non-Goals

- No migration work in any consuming app.
- No new shared package APIs unless a missing export blocks an accepted recipe and is recorded as an
  additive follow-up.
- No product-specific app examples, private route names, private fixture names, or private roadmap
  details in public docs.
- No full starter generator, CLI scaffold, template repository, or package publishing workflow.
- No broad rewrite of compatibility tests unrelated to the app-builder recipe shapes.
- No replacement for Storybook component detail or non-UI API docs completed in earlier tickets.

## Recipe Scope

The recipes should cover these app shapes:

| Recipe | Packages to Demonstrate | App-Owned Boundary |
| --- | --- | --- |
| Server app | UI, data, transport, automation | Auth, permissions, routes, services, schemas, repositories, fixtures, deployment target |
| Static blog | UI, automation/content, automation | Content collections, taxonomy, feed/search policy, layout, publishing workflow |
| Dashboard/admin tool | UI, data, transport, automation | Domain tables, filters, role policy, audit trail, mutations, seeded review data |
| Static demo | UI, automation static-site helpers | Browser state, local persistence, demo-specific copy, hosting target |
| Script consumer | Automation | Command list, environment, secrets policy, smoke journeys, release policy |
| Static-content generator | Automation/content | Source directories, metadata schema, document renderer, assets, base path |

Recipes may reference Walking Pace only when describing it as this repository's local reference app
or static demo. Public recipe examples should otherwise use generic names and values.

## Compatibility Requirements

- Compatibility tests should import from package paths such as:
  - `@macavitymadcap/hyper-dank-ui`
  - `@macavitymadcap/hyper-dank-ui/styles.css` where practical to verify the CSS export shape
  - `@macavitymadcap/hyper-dank-data`
  - `@macavitymadcap/hyper-dank-data/testing`
  - `@macavitymadcap/hyper-dank-transport`
  - `@macavitymadcap/hyper-dank-automation`
  - `@macavitymadcap/hyper-dank-automation/content`
- Tests should use fake inputs, in-memory stores, generated temporary files, or local static
  directories. They must not call live GitHub, deploy, email, database, or network services.
- Tests should assert observable contracts: rendered semantic HTML, HTMX/native attributes, provider
  lifecycle calls, migration execution, static content output paths, verification reports, server
  readiness helpers with fake fetches, and PR image Markdown.
- Existing private-consumer compatibility can remain as internal evidence if still useful, but public
  recipe coverage must have app-neutral names and app-neutral assertions.
- `bun run test:compat` should remain the main compatibility gate.

## Public Recipe Requirements

Each recipe should include the useful subset of:

- When to use the shape.
- Package imports involved.
- A small code example that composes public exports.
- What the package owns and what the application owns.
- Native HTML and HTMX fallback notes where applicable.
- Verification suggestions using repo/package helpers.
- Links to package API docs and Storybook for deeper component detail.

Keep recipe examples compact. A recipe should show the adoption pattern, not bury the reader in a
complete app.

## Implementation Notes

- Start with compatibility tests so the recipes describe protected package contracts rather than
  aspirational snippets.
- Prefer app-neutral filenames such as `e2e/consumer-compat/app-shapes.test.tsx` or a split by
  recipe shape if that improves scanability.
- Keep old private-consumer compatibility coverage only if it remains valuable as internal evidence;
  do not surface private names in public docs or recipe copy.
- Align recipe snippets with real compatibility examples. If a docs snippet cannot be tested exactly,
  test the same import path and rendered or behavioural contract.
- Do not add screenshot evidence for compatibility-only work. Add focused light/dark public docs
  screenshots only if the recipes page or navigation visibly changes.
- Use package README links to point readers towards the recipes rather than duplicating every recipe
  in each README.

## Acceptance Criteria

- `site/recipes.md` includes practical, app-neutral recipes for server app, static blog,
  dashboard/admin, static demo, script consumer, and static-content generator shapes.
- Each recipe names the public packages involved, gives a compact example, and states app-owned
  boundaries.
- Consumer-style compatibility tests import representative public exports for each recipe shape.
- Compatibility coverage includes the automation/content subpath and the data testing subpath where
  those APIs exist.
- Private consuming app names and private roadmap details do not appear in public recipes, package
  README examples, or app-neutral compatibility descriptions.
- Package READMEs and public docs link to recipes where that helps app builders choose a shape.
- `bun run test:compat` passes.
- `bun run verify` passes before the implementation PR is marked ready.
