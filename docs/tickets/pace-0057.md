## Summary

Make Storybook the canonical UI reference for `@macavitymadcap/hyper-dank-ui`. Every public shared
component should have discoverable Storybook coverage with useful examples, reference detail,
accessibility notes, light/dark review states, and focused interaction checks. Walking Pace domain
components should remain visible as reference-app composition examples, but clearly separated from
the generic package catalogue.

## Goals

- Audit the current Storybook catalogue against the public UI export boundary in
  `libs/components/src/index.ts` and the fixed component directory from
  `docs/architecture/app-builder-readiness-audit.md`.
- Add or deepen stories for every shared component exported by
  `@macavitymadcap/hyper-dank-ui`, including `Icon`, `Badge`, `Panel`, `Accordion`, `CompactList`,
  `PopoverMenu`, and the second-wave app-builder primitives.
- Use Hyper-Dank components inside Storybook guide/reference stories where practical so Storybook
  demonstrates its own component system rather than relying only on bespoke documentation markup.
- Keep Walking Pace molecules, organisms, pages, and templates in a separate
  `Components/Reference App` section that presents them as composition examples, not reusable
  package exports.
- Expand Storybook reference content with inputs, rendered output, events, accessibility
  expectations, HTMX/native fallback notes, CSS hook guidance, and ownership boundaries.
- Add or update Storybook browser checks and screenshot evidence for the shared catalogue and
  reference-app separation.

## Non-Goals

- No new shared UI components beyond coverage helpers or tiny story-only fixtures.
- No redesign of the Walking Pace app or public docs site.
- No migration of Walking Pace domain components into `@macavitymadcap/hyper-dank-ui`.
- No duplication of full component API reference in the public docs site; Storybook owns component
  detail for this ticket.
- No private consuming app names, private roadmaps, or product-specific future app requirements in
  Storybook copy.
- No visual screenshot refresh outside the Storybook surfaces changed by this ticket.

## Public API Requirements

- No breaking changes to `@macavitymadcap/hyper-dank-ui` exports.
- Any small component API additions discovered during story work must be additive, tested, exported,
  and documented in Storybook.
- Storybook references should use public package imports for shared components where practical.
- Story titles should preserve the agreed top-level groups:
  - `Introduction`
  - `Components/Shared`
  - `Components/Reference App`
  - `Guides`
- Shared component examples must avoid Walking Pace route names, fixture names, private consumer
  names, and domain-specific product copy.
- Reference-app examples may mention Walking Pace because they document the local reference app, but
  they must not imply those components are package exports.

## Storybook Reference Requirements

Each shared component reference should include the useful subset of:

- Purpose and when to use it.
- Key props, child structure, and variant or tone options.
- Rendered semantic output, landmarks, native element behaviour, and stable class hooks.
- Events and interactions such as links, buttons, forms, disclosure, dialog trigger behaviour,
  keyboard expectations, and focus movement.
- HTMX attributes or native fallback behaviour where the component participates in hypermedia flows.
- Accessibility notes for labels, `aria-*`, focus, headings, table semantics, and reduced-motion
  expectations where relevant.
- Light and dark examples, either through Storybook global theme review or explicit paired states.
- Composition examples for server apps, static blogs, dashboards/admin tools, docs/static demos, and
  reference-app surfaces without naming private consuming apps.

## Candidate Coverage

The exact story file layout may change during implementation, but coverage should include:

- Atoms: `Badge`, `Button`, `Card`, `Chip`, `Icon`, `IconButton`, `LinkButton`, `Panel`, `Switch`,
  `TableCell`.
- Actions and forms: `ButtonGroup`, `CheckboxField`, `Fieldset`, `FormField`, `HxForm`,
  `InputGroup`, `RadioGroup`, `SegmentedControl`, `SelectField`, `TextareaField`,
  `ValidationSummary`.
- Layout and navigation: `AppShell`, `Breadcrumbs`, `PageHeader`, `Pagination`, `SideNav`, `Tabs`,
  `Toolbar`.
- Feedback and overlays: `Callout`, `Dialog`, `EmptyState`, `LoadingIndicator`, `Notice`,
  `Progress`, `StatusSummary`.
- Data and content: `Accordion`, `CodeBlock`, `CompactList`, `LabelledOutput`, `MetadataList`,
  `PopoverMenu`, `Prose`, `ScrollableTable`, `SectionHeader`, `StatBlock`, `TimelineList`.
- Icon catalogue: include all currently exported generic icons, including light/dark mode icons
  such as `sun` and `moon`, plus app-builder icons needed by accepted recipes and reference-app
  examples.

## Implementation Notes

- Start by adding the catalogue coverage check so missing shared stories are visible.
- Prefer enriching existing story files when they already group related components clearly.
- Create dedicated stories for components that are currently only covered by aggregate examples if
  separate docs make the reference easier to scan.
- Keep story examples dense and practical: admin toolbar, static blog metadata, docs content, table
  actions, form validation, and dashboard status are better than marketing-style examples.
- Use shared Hyper-Dank components for Storybook docs pages where this improves consistency, but do
  not force awkward component use where plain semantic HTML is clearer.
- Use fixed viewport screenshots and scrolled states only where they prove relevant layout or
  navigation behaviour.
- Treat any discovered component API issue as a small fix only if it is required for accurate
  Storybook documentation; otherwise record it for a follow-up ticket.

## Acceptance Criteria

- Every public shared UI component export has Storybook coverage under `Components/Shared`.
- `Icon` has an explicit Storybook catalogue that includes light/dark mode icons and generic
  app-builder icons used by accepted recipes and reference-app examples.
- Storybook introduction and guide/reference stories use Hyper-Dank components where practical.
- Walking Pace domain components and app pages are grouped under `Components/Reference App` with
  copy that labels them as composition examples.
- Shared component Storybook docs include useful reference detail for props, output, events,
  accessibility, HTMX/native behaviour, CSS hooks, and ownership boundaries.
- Storybook browser tests cover representative render and interaction paths.
- PR screenshot evidence shows representative light and dark Storybook states for the shared
  catalogue, icon catalogue, documentation/guide composition, and reference-app section.
- `bun run verify` passes before the implementation PR is marked ready.
