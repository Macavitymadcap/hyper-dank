## Summary

Extract the reusable Markdown, front matter, page-route, URL-rewrite, and static-site build
mechanics from the current docs builder into a new automation package subpath:
`@macavitymadcap/hyper-dank-automation/content`.

The result should let server apps, docs sites, and static blogs reuse the boring content pipeline
parts without importing this repository's public docs site, Walking Pace app, navigation shell, CSS,
theme toggle, or GitHub Pages deployment assumptions.

## Goals

- Add a public `@macavitymadcap/hyper-dank-automation/content` subpath with typed exports.
- Extract front matter parsing, Markdown block rendering, inline rendering, table/code/list
  handling, raw HTML preservation, title derivation, route output-path helpers, and URL rewriting
  into reusable pure helpers.
- Provide a small static-content build helper that reads Markdown files, returns page models, and
  writes pretty-route HTML through an app-provided document renderer.
- Keep docs-site presentation local to `apps/walking-pace/scripts/lib/docs-build.ts`: site chrome,
  nav links, theme-toggle markup, code-highlighting includes, CSS assets, and Pages artifact layout
  remain app/repo-owned.
- Update package exports, declaration build, README coverage, public docs references, and consumer
  compatibility tests for the new content subpath.
- Keep the existing GitHub Pages docs build behaviour unchanged while moving reusable mechanics
  behind the shared helper APIs.

## Non-Goals

- No full static-site framework, routing framework, theme system, RSS/search/taxonomy engine, or
  client-side hydration layer.
- No dependency on the Walking Pace app, the public docs site shell, Jekyll/Liquid as a full
  template language, or GitHub Pages as the only deployment target.
- No blog domain model, comments, authorship workflow, draft publishing policy, or content
  collection schema beyond generic front matter metadata.
- No visual redesign of the docs site or Storybook.
- No replacement for mature Markdown libraries unless the implementation first proves the current
  small parser should be swapped and updates this ticket.
- No private consuming app names, private content paths, or roadmap details in public docs or
  examples.

## Public API Requirements

- Add `./content` to `libs/scripts/package.json` exports with `types` and `import` entries.
- Exports must be additive and typed; existing root automation exports remain backwards compatible.
- Public API names should be generic: content, Markdown, page, route, front matter, URL, asset.
- Helpers must not assume Hyper-Dank docs navigation, Walking Pace paths, GitHub Pages base paths,
  highlight.js CDN links, or a particular visual shell.
- Error messages should identify the content file/path or invalid route where practical.
- Package README and public docs must describe functions, types, parameters, returns, errors, and
  examples in prose, not only tables.
- Consumer compatibility must import the packaged `/content` subpath and exercise a static blog or
  docs-site shape.

## Candidate Interfaces

The exact names may change during implementation, but the ticket should stay within this boundary:

- `parseFrontMatter(content)` returning `{ frontMatter, body }`.
- `renderMarkdown(markdown, options)` with app-provided URL/base-path behaviour and raw HTML
  preservation matching the current docs build.
- `renderInlineMarkdown(value, options)` or equivalent for links, code spans, strong text, escaping,
  and relative URL rewriting.
- `discoverMarkdownPages({ sourceDir })` or `readContentPages()` for Markdown files plus metadata.
- `outputPathForContentPage(fileName, permalink)` and `titleFromFilename(fileName)`.
- `buildStaticContentSite({ sourceDir, destinationDir, renderDocument, assets })` or a narrower
  helper that writes discovered pages through an app-owned document renderer.
- `rewriteContentUrl(url, options)` and `relativeContentUrl(url, basePath)` helpers that do not
  require GitHub Pages.

Avoid exposing the current docs-site `renderDocument()`, theme toggle HTML, code-highlighting tags,
or nav shell as shared package API.

## Implementation Notes

- Start by adding tests under `libs/scripts/src/content/*.test.ts`; move implementation only after
  the shared behaviour is pinned.
- Keep the app-local `docs-build.ts` as the owner of Hyper-Dank docs chrome and Pages integration.
- Prefer pure functions with explicit options over global config.
- Preserve current docs rendering behaviour unless a bug is found and documented in this ticket or
  the implementation PR.
- Ensure package declaration output includes the new subpath.
- Update `e2e/consumer-compat/character-sheet-compat.test.tsx` only with app-neutral package-shape
  imports and examples; do not mention private consuming apps in public docs.

## Acceptance Criteria

- `@macavitymadcap/hyper-dank-automation/content` is exported with TypeScript declarations.
- Front matter, Markdown rendering, route/output-path, title, URL rewrite, and static build helpers
  are available as reusable, app-neutral APIs.
- Existing docs build behaviour remains stable, including pretty routes, copied assets, raw HTML
  preservation, code blocks, tables, and base-path URL rewriting.
- Automation README and public docs describe the content APIs and boundaries with examples.
- Consumer compatibility tests import and exercise the new `/content` subpath.
- No shared content helper imports Walking Pace app code, docs-site layout files, or deployment
  scripts.
- `bun run verify` passes before the implementation PR is marked ready.
